# Explicit operator lifecycle

This external tool manages exact thin Git hooks and operator-owned canary records. It never decides quality, pushes commits, changes branch rules or schedules agents. Core is not a library dependency. The hooks filesystem implementation is retained from GateHouse 578a16befdc0017e1cf8d3021fc964d86cf23ad4, including lock ownership, byte identity, no-clobber creation and rollback of only files created by the operation.

Use `gateprobes-operator --project-root /project hooks --core /protected/harness-gate --core-sha256 <reviewed-sha256> install` (or status/uninstall). The protected Core binary is inspected read-only with `config print --resolved`; workloads are never run during installation. Existing managed hook bytes remain unchanged and still invoke harness-gate hook/verify on PATH when Git later runs them. Protect PATH/Core separately. Custom hooksPath, symlink and modified/foreign hooks remain rejected. No live repository hook installation is performed by release acceptance.

Hook and lock removal is non-destructive. Each object is moved to `object` inside a private `.harness-gate-preserve-<random>` directory created in the hooks directory, and the moved inode is never unlinked. Only an exact managed object frees its hook path, and its bytes stay in that backup. Any other object (foreign, modified, symlink, directory, or a restore conflict) is restored no-clobber by a hard link where possible; the backup hard link is kept even after a successful restore, so removing the hook path later still leaves the backup. There is no automatic recovery, rollback, pruning or deletion of backups. `status` is read-only: it lists retained objects with exact escaped paths and logical sizes, and reports an ordinary backup only as a warning. The scan is bounded to 1024 total entries in the hooks directory; exceeding that bound, or any scan error, fails the command without changes instead of returning a truncated result. Capacity is not capped: backups accumulate until an operator removes them, 16 KiB is only the inspection read cap (a descriptor opened before isolation can keep growing the retained object), and the reported size is logical object size, not disk usage or recursive size. Retention is guaranteed only for process exit; the backup directory is not fsynced, so power-loss durability is not promised. This protects the normal editor path under a trusted hooks directory with stable ancestors; it is not isolation from a malicious same-user process that replaces directories, and external interference with the cooperative lock already breaks mutual exclusion. Directory objects and restore conflicts are retained for manual inspection: stop other writers, verify ownership and the exact backup path, then recover manually; never blind-overwrite or delete with wildcards. The implementation is `cfg(unix)`, so it also compiles and applies on macOS; only Linux is certified and tested, other Unix platforms are not validated, and non-Unix keeps the previous identity-checked removal behaviour without a cross-platform guarantee. Fault-injection hooks exist only in source tests; the release binary has no injection support.

`canary --state /operator/state.json --slice team-a` and `rollback --state /operator/state.json` maintain the existing version1 external record shape only. Core never reads these markers; they are not a deployment, enforcement or rollback engine. State directories must be operator-protected and have a single writer. Existing markers and installed hooks are not changed automatically during migration. Core management commands have been migrated out of Core; the existing script execution interface remains available.

Support is initially Linux x86_64. A bounded read-only child inspection is not hostile-process isolation. Private files and tokens must not be accessible to workload code. No production host state is modified during testing.
